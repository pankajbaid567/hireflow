# HireFlow milestone audit

Audit date: **23 October 2026 (IST)**. Specification: [MILESTONES.md](../MILESTONES.md), supplemented by the later issue acceptance criteria. This is an acceptance audit, not a claim that every milestone is complete. **All eight milestones still have gaps against the original specification.** Working source, a passing mock test, and a successful production workflow are different evidence.

Two implementations now coexist:

- **Python/Docker:** FastAPI, SQLAlchemy/PostgreSQL, local Playwright, ReportLab, optional sentence-transformers/FAISS. This remains the original implementation under `src/`.
- **Cloudflare:** TypeScript Worker, D1, private KV files with an optional R2 adapter, Queues, and Browser Run under `cloudflare/`. The React dashboard shares its API contract. This is an intentional deployment adaptation; it does not run Python, PostgreSQL, or FAISS on Workers.

The frontend is deployed at **https://hireflow-dashboard.pages.dev**, with the API at **https://hireflow-api.baidpankaj567.workers.dev**. Pages forwards private `/api/*` requests through its `API` service binding. Vercel remains a temporary old-cookie migration bridge. D1 migrations 0001–0003 are applied. Deployment and a completed browser workflow are separate verification gates; see the evidence below.

## Status definitions

| Status | Meaning |
|---|---|
| Implemented | The stated behavior exists in the named implementation and has relevant local tests. This does not imply every portal or a production delivery has been tested. |
| Partial | Some required behavior exists, but an acceptance condition, normal-path integration, or substantive coverage is missing. |
| Missing | The reviewed normal execution path does not implement the requirement. |
| Unverified | Code or configuration exists, but the relevant real integration or deployment has not been proved. |

## Verified release and remaining acceptance work

The reported sparse profile/PDF, expired-vacancy classification, production job discovery, Pages migration, individual review, persistent company exclusion and strict controlled production UI cycle are repaired and verified above. The remaining original-spec requirements are:

1. **Improve discovery quality before claiming scale.** Demonstrate real active source pages/full JDs from the UI, reliable expiration/company/title checks, persisted source/compensation/requirements, calibrated spam handling and meaningful mode/geography filters. Then measure a 100+ cycle without exceeding provider or Workers CPU budgets.
2. **Resolve matching/tailoring scope.** Either integrate/evaluate actual embeddings + vector retrieval and LLM role/mode summaries, or keep the documented matching scope as lexical. Grounded JD/mode-specific Groq selection is now integrated in the normal preparation path and has actual-provider evidence. Verify the new INR salary comparison and finish structured currency/pay-period handling. Never manufacture missing accomplishments to improve a resume.
3. **Close workflow features deliberately.** Multi-step ATS checkpoints, per-listing resume editing/reapproval, prep exports, mixed-mode reports, verified email delivery and a consent-preserving weekly scheduler need explicit implementation/acceptance work. Individual review was verified in the production UI cycle; batch behavior also has local coverage.
4. **Finish the optional module and documentation only when claimed.** Hiring-team export/email, actual applicant parsing, architecture diagram, demo video, truthful README, fresh-machine setup and CI results remain separate deliverables.

## Reproducing checks

These default checks use isolated fixtures/mocks and do not send real emails or submit external employer applications:

```bash
python -m pytest -q  # activate the configured project virtualenv first
cd frontend
npm ci
npm test -- --run
npm run build
cd ../cloudflare
npm ci
npm run check
```

Use **Node 22 or later** for the Cloudflare tooling. Local automation tests need the installed Playwright Chromium binary. Docker setup and migration commands are documented in [deployment.md](deployment.md); [cloudflare.md](cloudflare.md) describes the alternative runtime. A successful local command is not evidence that a remote CI job has executed.

The opt-in provider tests and scripts under `scripts/verify_cloudflare_live*` incur actual provider/browser usage and create synthetic private records. They require the configured credentials and explicit run switches. They must target the controlled QA form only, use fresh synthetic identities, retain strict fact/status assertions, and keep credentials/cookies out of logs. The strict UI script defaults to Pages and separately verifies migration from the old Vercel origin. The older API script is a separate opt-in controlled check. Root owns scoped synthetic-record cleanup; do not delete or overwrite the real user's profile/applications.
