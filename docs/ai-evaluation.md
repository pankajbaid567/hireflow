# AI evaluation and matching evidence

The benchmark is versioned at [`evals/hireflow_v1`](../evals/hireflow_v1/manifest.json).
It contains **120 entirely synthetic labelled cases**, with invented candidates,
projects, employers and `example.com` contacts. No production resume or private
workspace was copied. Labels express an authored relevance/factuality rubric;
they are **not independently human-annotated hiring outcomes**.

## Dataset, controls and what is measured

| Task | Distinct cases | Actual path exercised |
| --- | ---: | --- |
| Ranking | 48 queries, five candidate JDs each | Current Worker `scoreMatch`, genuine frozen BGE vectors, pure cosine and technical-factor hybrid scores. |
| Extraction | 24 labelled source texts; fixed six-case live subset | Normal Python Groq profile-extraction prompt/parser, including fresher/experienced totals, JavaScript/Go skills, a Latin-accented name and an adversarial note. PDF intake/rendering is separately covered by [P1-08 evidence](p1-pdf-quality.md). |
| Resume selection | 24 | Current Worker factual fallback, selected project recall and exact source preservation; two additional actual Groq selections use the same cases. |
| Preparation | 16 | Current Worker fallback questions: skill/domain-context coverage, category/round correctness, cross-case duplication; each case also exercises a controlled source-support scenario. |
| Adversarial/provider recovery | 8 | Current Worker factual-selection guards under missing config, rate limit, outage, malformed selection, invented evidence, invalid project index, timeout and injected instructions. |

Ranking has **28 development and 20 heldout queries**, split by domain group.
No ranking domain appears in both splits. Other task families reuse some invented
domains; they must not be used to tune heldout ranking. Two mode variants share a
family, so this is a compact correlated benchmark, not 120 independent samples
from the Indian hiring market.

The corpus SHA-256 and adoption thresholds were frozen before inference in
[`manifest.json`](../evals/hireflow_v1/manifest.json). The fixed hybrid alpha is
0.2. Adoption requires heldout nDCG@3 improvement of at least 0.03, Recall@1
improvement of at least 0.05, and no Recall@3 regression greater than 0.02.
Never tune thresholds, labels or alpha after inspecting these heldout results;
create a new benchmark/version when the study changes.

## Ranking result and adoption decision

The **actual Worker scoring functions**, not a reimplementation of their
lexical formula, produced these results in
[`offline.json`](../evals/results/offline.json):

| Heldout method | Recall@1 | Recall@3 | nDCG@3 |
| --- | ---: | ---: | ---: |
| Lexical six-factor baseline | 0.3000 | 0.8000 | 0.6991 |
| Genuine BGE cosine only | 0.5000 | 1.0000 | 0.9458 |
| Technical-factor hybrid | 0.5000 | 1.0000 | 0.9511 |

The predeclared adoption gate passed. The benchmark deliberately includes
near-ties where stack overlap cannot distinguish a candidate's evidenced project
domain, along with absent-stack negatives. It demonstrates an improvement on
these tasks; it does not establish a general hiring-success improvement or a
calibrated probability. Report error analysis per query rather than only a mean:
heldout examples still fall short of perfect graded order despite full Recall@3.

The original **40/20/15/10/10/5 factor weights remain unchanged**. Only the
technical factor becomes `0.8 × explicit skill coverage + 0.2 × cosine`.
Consequently the overall semantic contribution is at most 0.08. Explicit
matched/missing skills remain exact explanations; high semantic similarity never
adds a skill to the resume. Ties retain deterministic job/application-ID order.

### Real model and provenance

The public frozen artifact was generated by **BAAI/bge-small-en-v1.5**, revision
`5c38ec7c405ec4b44b94cc5a9bb96e735b38267a`, with **CLS pooling and 384 dimensions**.
The recorded local CPU run loaded the model in 5,618 ms and encoded 218 unique
texts in 854 ms. This is measured local inference, **not Cloudflare inference
latency**. The vectors are genuine model outputs rounded to seven decimal places,
with corpus and exact input hashes, so default CI can check ranking without
network/model downloads.

Production uses the separate Workers AI binding and
[`@cf/baai/bge-small-en-v1.5`](https://developers.cloudflare.com/workers-ai/models/bge-small-en-v1.5/).
It requests CLS explicitly, uses private D1 vector caches, and never tries to run
FAISS in a Worker. A production binding/UI check is separate from this local
model qualification; release proof must name it explicitly. Provider-managed
weights can change independently of this recorded local revision.

## Factuality, extraction and preparation

The 24 deterministic selection cases retained source experience/education and
selected at least one labelled relevant project in every case, with **zero
unsupported claims**. All eight provider/adversarial fixtures retained factual
fallbacks. These checks evaluate the source-selection guard, not open-ended
model-writing quality.

Two actual Groq `openai/gpt-oss-20b` calls returned **`llm_grounded`** selections,
zero unsupported claims and full labelled project recall in 721/757 ms. See
[`live-tailoring.json`](../evals/results/live-tailoring.json). This small live
sample must not be generalized to every provider/output.

The first fixed six-case Groq extraction run returned **29/30 correct labelled
fields**, with zero invented employment claims. One development case explicitly
stated three years of professional experience, but its numeric total was lost
when no individual role rows were listed. A narrow deterministic guard now
preserves an unambiguous standalone aggregate, including explicit zero; it does
not infer years from role counts, dates, project durations, ranges or instructions.
Regression tests cover those boundaries. The unchanged fixed subset rerun
returned **30/30 fields**, zero unsupported employment claims, in 7.721 seconds.
Both the [baseline](../evals/results/extraction-live-baseline.json) and
[corrected run](../evals/results/extraction-live.json) are retained. This was a
development-case correction, not heldout ranking tuning. Six cases are actual
provider evidence; the other 18 extraction sources are labelled but unmeasured
by this text-provider run.

The 16 preparation cases covered all requested categories, named the JD skills
and respected explicit round counts. Specificity is measured beyond skill names:
**all technical/design questions included the case's actual JD requirement
span**. Behavioral questions had **zero full requirement-span coverage** and an
**87.5% cross-case duplicate rate**; across all questions the duplicate rate was
21.875%. These are concrete weaknesses in the fallback, not hidden by a perfect
skill-mention score. Improving behavioral distinctiveness/usefulness remains the
preparation-quality backlog; the human rubric must assess usefulness beyond
these lexical coverage metrics.

Each of those existing cases also runs the actual `buildPrepGuide` against
[versioned controlled sources](../evals/hireflow_v1/source_support_fixtures.json).
The 16 source scenarios issued 206 **intercepted fixture fetches, no network
requests**. All **66 emitted company claims** matched the synthetic source facts,
with zero unsupported claims/URLs. The scenarios verify positive fact/claim
support, missing-source abstention, old/future-news rejection, missing-review
guidance and skipping broken resources in favor of two working fixture links per
topic. These are additional scenarios on the same cases, not 16 extra independent
labelled cases. The fixture version/digest and individual results are recorded.
This supplements measurement without changing the frozen ranking labels, alpha
or adoption thresholds.

With no search provider configured, the separate actual fallback emitted **zero
unsupported company claims** and kept unknown facts. Its resource/source
precision remains **null**, not perfect by vacuous absence of links. Controlled
fixture claim precision must **not** be presented as live website factuality or
resource relevance. Full-page/source contradictions, current external resource
usefulness and independent human/source review remain unmeasured here and belong
to the preparation/source-quality work.

## Human review rubric

This review protocol follows the project's factuality, JD-specificity and
source-support acceptance requirements. Automated evidence is not a substitute
for human judgement of usefulness. An independent maintainer review has **not
been recorded**; never label the synthetic judgments as human ratings.

| Dimension | 0 | 1 | 2 | Reviewer evidence |
| --- | --- | --- | --- | --- |
| Factual preservation | Invented/lost material source fact | Nonmaterial omission or ambiguous wording | Every material claim traceable to the source | Quote the exact source fact and output clause. |
| Ranking relevance | Required stack/level incompatible | Plausible adjacent fit with stated gaps | Direct fit supported by profile evidence | Cite JD requirement and profile evidence; ignore protected traits. |
| Resume selection | Irrelevant or invented evidence | Partially relevant truthful selection | Most relevant truthful projects/facts | Name selected/omitted project IDs and why. |
| Question usefulness | Generic, unsupported or wrong level | Some JD context, uneven difficulty | JD-specific and suitable for the mode | Identify the JD skill/requirement and expected depth. |
| Source support | Fabricated or inaccessible attribution | Useful but incomplete evidence | Accessible source directly supports the claim | Record URL, access date and exact supported claim. |

For an independent review, use two reviewers on a blinded sample from both
splits, retain their disagreement/adjudication notes and review date, and keep
those ratings separate from the current authored labels. Do not use an LLM
judge as the sole factuality authority or silently overwrite frozen labels.

## Actual Python plan integration

The [real-model API proof](../evals/results/python-plan-real-model.json) called the
normal authenticated `GET /weekly-plan/{id}` route on a fresh private SQLite
workspace. It loaded the cached BGE revision/CLS model on Apple MPS and invoked
the real FAISS index/search, with no injected model vectors. Two candidates tied
lexically at 0.725; their real cosine scores were 0.7570/0.8567 and hybrid scores
0.7056/0.7135. The normal plan selected the second, context-relevant candidate,
persisted `matching_method: hybrid` and prepared its truthful PDF. No employer
request, model download, provider call, confirmation or email occurred; logout
revoked private reads. This proves normal-path integration, not an unused helper.

The proof is reproducible with `venv/bin/python
scripts/verify_python_semantic_plan.py --run-local` after the public BGE model is
cached and optional embedding dependencies are installed. The explicit flag is
required; the check creates only a temporary synthetic SQLite workspace. Its
8.406-second wall time includes first model loading and PDF preparation on this
host, not Cloudflare request CPU or general production latency.

## Budget, privacy and failure behavior

Worker matching reserves at most **100 embedding texts/day globally**, atomically,
with an eight-second inference abort and at most 20 candidate jobs per call.
The cache namespace includes model, pooling, algorithm, owner, profile version
and complete source hashes. Edits cannot reuse a stale vector. The request text
is capped at 1,800 characters and omits intentionally supplied identity/contact
fields; unhelpful contact details inside summaries are scrubbed. The model's
published token limit still applies; an inaccessible/invalid/over-budget result
uses explicitly labelled lexical scores. An uncertain provider attempt does not
refund its reservation. Caches remain private and owner deletion cascades them. Scheduled pruning removes
recomputable vectors older than 30 days and usage history older than seven days;
it never refunds current-day reservations or deletes submitted PDFs/history.

Workers AI has a [free daily allocation](https://developers.cloudflare.com/workers-ai/platform/pricing/),
but this benchmark does not claim to have measured an account bill. Local
embedding inference made no hosted requests. Live extraction/tailoring wrappers
do not expose full token/billing usage, so those report fields remain **null**,
not zero. Logical request counts, measured wall latency, provider failure and
actual method are recorded. The before/after extraction runs plus live tailoring
used 14 logical provider operations in total; raw transport retries are unknown
within the normal client's bounded retry setting.

Python's normal `score_jobs_for_user` route calls the genuine FAISS helper when
`SEMANTIC_MATCHING_ENABLED=true`; optional model dependencies must be installed.
It uses an owner-private, source/model-versioned disk cache and a bounded
200-candidate lexical pool. Missing dependencies/provider failures retain
lexical metadata. Its default is now the same public BGE model with native CLS pooling, while
existing user configuration may select a different model. The table above
qualifies the stated BGE configuration, not arbitrary replacement models. Applied/history scores are not rewritten.

## Reproduce

Use Node 22+ and the project Python environment. Default evaluation uses only
public frozen vectors, actual local functions and controlled provider fixtures:

```bash
node scripts/run_ai_evaluation.mjs
venv/bin/python -m pytest tests/test_evaluation_corpus.py tests/test_semantic_matching.py tests/test_extraction_evaluation_regressions.py -q
```

To regenerate genuine vectors, install the optional embedding dependencies and
run `PYTHONPATH=. venv/bin/python evals/embed_corpus.py`. This can download the
public model; it reads no provider key. Verify model revision/pooling and input
hashes before replacing a frozen artifact.

Actual provider calls are explicit opt-in and use only synthetic sources:

```bash
node scripts/run_ai_evaluation.mjs --live-tailoring --output /tmp/hireflow-live-tailoring.json
PYTHONPATH=. venv/bin/python evals/run_live_extraction.py --run-live --output /tmp/hireflow-live-extraction.json
```

Do not put real resumes, account credentials, provider keys or cookies in this
public corpus. Provider success today does not guarantee future availability.

## P2 preparation comparison

The P1 preparation baseline above is retained at
[`evals/prep_v2/baseline-p1.json`](../evals/prep_v2/baseline-p1.json).
The separately versioned P2 evaluator compares the same known cases, removes
company/project labels before duplicate checks and measures responsibility-token
coverage in the actual question text. Behavioral duplicates improve from 87.5%
to 0%, with zero near-duplicates at Jaccard 0.85 and full goal-token coverage on
these cases. This is known-case regression evidence rather than a new blind
holdout or human quality assessment. Full policy, source and refresh limitations
are documented in [P2 preparation quality](p2-preparation-quality.md).
